## Choose your deployment

Both methods run the same Nitro binary with the same configuration. They differ in what surrounds it.

|               | Docker                                                  | Helm on Kubernetes                                                    |
| :------------ | :------------------------------------------------------ | :-------------------------------------------------------------------- |
| Best for      | A single host, a first node, local testing              | A cluster, and nodes you operate long-term                            |
| Configuration | CLI flags on `docker run`, or a `node-config.json` file | Chart values under `configmap.data.*`, as `--set` or a values file    |
| Memory limits | You set `GOMEMLIMIT` yourself                           | The chart derives `GOMEMLIMIT` from the pod's memory limit            |
| Monitoring    | You scrape the metrics port yourself                    | A `ServiceMonitor` for Prometheus, plus a published Grafana dashboard |
| Health checks | You add them                                            | A startup probe ships on by default; you add liveness and readiness   |
| Storage       | A host directory you mount                              | A PersistentVolumeClaim sized by `persistence.size`                   |

The chart is the [community Helm chart](https://github.com/OffchainLabs/community-helm-charts/tree/main/charts/nitro). Its defaults target Arbitrum One, so Arbitrum One is the worked example throughout. Each step notes what changes for other chains.

### Parent chain (L1) client

Your node needs a parent chain RPC endpoint, and that client must stay up to date. An incompatible L1 client version can crash your Arbitrum node or stop it from syncing, so check the [Nitro release notes](https://github.com/OffchainLabs/nitro/releases) when you upgrade it.

Arbitrum One, Nova, and Sepolia settle to Ethereum, so they also need an L1 beacon or blob endpoint. See [L1 Ethereum beacon chain RPC providers](/run-arbitrum-node/reference/l1-ethereum-beacon-chain-rpc-providers.mdx). For a chain with a different parent, use that parent chain's RPC, and add a beacon endpoint only if the chain posts blobs.

### Recommended Nitro version

Latest [Docker image](https://hub.docker.com/r/offchainlabs/nitro-node/tags): <code>@@latestNitroNodeImage=offchainlabs/nitro-node:v3.11.3-beb2108@@</code>

The Helm chart pulls the same image. Pin it with `image.tag` rather than tracking the chart's default.

<VanillaAdmonition type="caution">

Run only release versions. Beta and release candidate builds of Nitro are not supported and can cause unexpected behavior or database corruption.

</VanillaAdmonition>

### Choose a state scheme

Nitro stores its state trie using one of two <a data-quicklook-from="state-scheme">schemes</a>: **<a data-quicklook-from="hashdb">HashDB</a>** (the default) or **<a data-quicklook-from="pathdb">PathDB</a>**. Choose before you initialize the database. You cannot switch an existing database — moving between schemes means re-initializing from a snapshot built with the scheme you want.

| Property                      | HashDB (default)                         | PathDB                                     |
| :---------------------------- | :--------------------------------------- | :----------------------------------------- |
| Flag                          | None; Nitro uses HashDB by default       | `--execution.caching.state-scheme=path`    |
| State trie pruning            | Manual and offline, via `--init.prune`   | Automatic and online                       |
| Block validation              | Supported                                | Not supported                              |
| Full node snapshot            | `pruned`, all three DAO-governed chains  | `full-path`, all three DAO-governed chains |
| Archive snapshot              | `archive`, all three DAO-governed chains | `archive-path`, Arbitrum One and Sepolia   |
| Download with `--init.latest` | Supported                                | Not supported; use `--init.url`            |
| Minimum Nitro version         | Any                                      | v3.9.x                                     |

Pick based on how you want to handle <a data-quicklook-from="state-pruning">pruning</a> and whether you need block validation:

- **Choose HashDB** if your node runs the block validator, or if you want the simplest initialization. `--init.latest pruned` downloads and verifies the snapshot for you. You then prune manually, and your node is offline while it does.
- **Choose PathDB** to avoid manual prune cycles. Nitro prunes online, so the node keeps serving RPC and disk use stays within the window you set with `--execution.caching.state-history`. You pass the snapshot URL to `--init.url` yourself.

On archive nodes, PathDB cuts disk use substantially. See [how to run an archive node](/run-arbitrum-node/more-types/01-run-archive-node.mdx).

<VanillaAdmonition type="warning" title="PathDB and block validation">

PathDB cannot validate blocks. Nitro rejects `path` and exits at startup with `path cannot be used as execution.caching.state-scheme when validator is required` when you set `--node.block-validator.enable=true`, choose a staker strategy other than `Watchtower`, or enable fast confirmation. A default full node runs Watchtower, so it is unaffected.

</VanillaAdmonition>

### Database snapshots

Whether you need a <a data-quicklook-from="database-snapshot">database snapshot</a> depends on the chain:

- **Arbitrum One** requires one on the first run, because the snapshot supplies state from the Classic era.
- **Arbitrum Nova and Sepolia** have published snapshots that speed up the initial sync but are not required.
- **Your own Arbitrum chain** typically syncs from genesis, unless the chain's team publishes a snapshot for you.

A snapshot gives your node the chain's state up to a specific block, so it reaches the head of the chain faster. Initial sync still takes hours to days. Snapshots for Arbitrum One, Nova, and Sepolia are listed in the [snapshot explorer](https://snapshot-explorer.arbitrum.io/).

Initialize with one of two flags:

- `--init.latest <kind>` downloads and verifies the latest snapshot of that kind from `https://snapshot.arbitrum.foundation/`. It accepts `pruned`, `archive`, and `genesis`, and every kind it resolves uses HashDB. Override the base URL with `--init.latest-base`.
- `--init.url <url>` takes a snapshot URL directly. Use it for the PathDB kinds, `full-path` and `archive-path`, which `--init.latest` does not accept.

Nitro ignores both flags once a database exists, so it is safe to leave them in place across restarts.

<VanillaAdmonition type="warning" title="Match the snapshot to your state scheme">

A snapshot only works with a node running the same state scheme. Each snapshot directory publishes a `metadata.json` file naming its `state_scheme`. Check it before you download.

</VanillaAdmonition>

Read [Nitro database snapshots](/run-arbitrum-node/reference/nitro-database-snapshots.mdx) for every snapshot kind, [PathDB initialization](/run-arbitrum-node/reference/nitro-database-snapshots.mdx#pathdb-snapshots), and [hosting one snapshot for several nodes](/run-arbitrum-node/reference/nitro-database-snapshots.mdx#downloading-the-snapshot-manually).

<VanillaAdmonition type="warning" title="Fusaka upgrade: historical blobs">

If you run a beacon node, historical data now lives in <a data-quicklook-from="blob">blobs</a>. To make this transition, see [historical blobs for beacon nodes](/run-arbitrum-node/data-availability/beacon-nodes-historical-blobs.mdx).

</VanillaAdmonition>

## Configure and tune the node

### Watchtower mode

By default, the full node runs in Watchtower mode. It watches the onchain assertions and, if it disagrees with them, logs an error containing the string `found incorrect assertion in watchtower mode`.

- Watchtower mode is optional and adds a small amount of execution and memory overhead. Turn it off with `--node.staker.enable=false`. Your node serves RPC and follows the chain either way.
- On a BoLD-enabled chain such as Arbitrum One or Nova, if you run Nitro before v3.6.0, set `--node.bold.enable=true` so your node monitors onchain assertions properly.
- For watchtower mode alongside the other validator strategies (`defensive`, `stakeLatest`, `resolveNodes`, `makeNodes`), see [how to run a validator](/run-arbitrum-node/more-types/02-run-validator-node.mdx).

### Pruning

Pruning removes older state from the local copy of the chain your node maintains. It saves disk space and slightly improves the node's efficiency. How you prune depends on the [state scheme](#choose-a-state-scheme) you chose.

On **PathDB**, Nitro prunes automatically and online. It discards state older than the `--execution.caching.state-history` window as it goes, so you never schedule a prune and the node never goes offline to run one.

<StateHistoryDefaults />

On **HashDB**, the default, pruning is manual and opt-in. It runs at startup, during initialization, and the node stops serving RPC requests until it finishes. Activate it with `--init.prune <mode>`:

| Mode        | Retains                                                                                                    | Use for                                                                                                                                                        |
| :---------- | :--------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `minimal`   | Genesis state and head state only                                                                          | The fastest and most aggressive prune                                                                                                                          |
| `full`      | Genesis state, the latest confirmed block, and head state                                                  | Full nodes serving RPC. It does not work in `validator` mode.                                                                                                  |
| `validator` | The `full` set, plus the latest confirmed assertion root from L1 and the last locally validated block root | Validators. Needs an L1 Ethereum RPC URL, and takes longer than `full`. See [how to run a validator](/run-arbitrum-node/more-types/02-run-validator-node.mdx). |

Duration scales with database size: several hours on smaller chains, and multiple days on Arbitrum One even on NVMe SSDs. If a prune runs too long, download a fresh snapshot with `--init.latest pruned` instead.

### Memory management

Under heavy RPC load, or during operations such as large `debug_traceBlockByNumber` calls, Nitro nodes can consume significant memory. Two settings prevent out-of-memory (OOM) crashes:

- `--node.resource-mgmt.mem-free-limit`: Declines incoming RPC requests when free system memory drops below the specified threshold, for example `--node.resource-mgmt.mem-free-limit=4GiB`.
- `GOMEMLIMIT`: Sets a soft memory limit for the Go runtime garbage collector, for example `GOMEMLIMIT=48GiB` for a 64 GB machine. This reduces memory spikes.

For Nitro's memory allocators, cache tuning, and OOM mitigations, see [node tuning and monitoring](/run-arbitrum-node/operation/node-tuning-and-monitoring.mdx).

- **`resources.limits.memory`**: set this to activate the chart's automatic `GOMEMLIMIT`. When a memory limit is present, the chart derives `GOMEMLIMIT` from it (`env.nitro.goMemLimit`, on by default).
- **`MALLOC_ARENA_MAX=2`**: the chart sets this by default (`env.nitro.mallocArenaMax`), so you do not normally need to configure it.
- **`configmap.data.node.resource-mgmt.mem-free-limit`**: the RPC memory throttle, disabled by default. Recommended if you expose this node as a public RPC.

To set any other environment variable, use `extraEnv`, whose entries are spliced directly into the pod's `env`:

```yaml

  - name: SOME_VAR
```

## Network egress allowlist

A full node reaches out to a fixed set of endpoints. Cloud providers often restrict outbound traffic by default, so you may need to allow these destinations in your security group, firewall rules, or egress `NetworkPolicy`.

For DAO-governed chains, the hostnames come from the chain's built-in chain info. For your own Arbitrum chain, they come from the `chain.info-json`, `execution.forwarding-target`, and feed URLs you configure. The categories are the same across chains:

| Purpose                       | Where the endpoint comes from                                       | When                                        |
| :---------------------------- | :------------------------------------------------------------------ | :------------------------------------------ |
| **Sequencer** (tx forwarding) | chain info `sequencer-url` / `execution.forwarding-target`          | Always—the node forwards user txs here      |
| Sequencer fallbacks           | chain info `secondary-forwarding-target`                            | Failover                                    |
| **Sequencer feed**            | chain info `feed-url` / `node.feed.input.url`                       | Always                                      |
| Feed fallbacks / delayed      | chain info `secondary-feed-url` / `node.feed.input.secondary-url`   | Failover                                    |
| Block metadata                | chain info `block-metadata-url`                                     | Only if tracking block metadata / Timeboost |
| DB snapshot                   | the `init` source host                                              | Initial sync only                           |
| **Parent chain**              | your parent-chain RPC + beacon (beacon only for an Ethereum parent) | Always                                      |
| DA / REST endpoints           | `rest-aggregator` URL list                                          | AnyTrust chains only, such as Nova          |

For **Arbitrum One**, those resolve to:

| Purpose                   | Endpoint(s)                                                                                    |
| :------------------------ | :--------------------------------------------------------------------------------------------- |
| Sequencer (tx forwarding) | `https://arb1-sequencer.arbitrum.io/rpc`                                                       |
| Sequencer fallbacks       | `https://arb1-sequencer-fallback-{1..5}.arbitrum.io/rpc`                                       |
| Sequencer feed (primary)  | `wss://arb1-feed.arbitrum.io/feed`                                                             |
| Feed fallbacks / delayed  | `wss://arb1-delayed-feed.arbitrum.io/feed`, `wss://arb1-feed-fallback-{1..5}.arbitrum.io/feed` |
| Block metadata            | `https://arb1.arbitrum.io/rpc`                                                                 |
| DB snapshot               | `https://snapshot.arbitrum.foundation/`                                                        |
| Parent chain              | Your Ethereum L1 execution RPC + L1 beacon/blob endpoint                                       |

<VanillaAdmonition type="caution" title="Firewall egress">

For a default Arbitrum One full node, allow `*.arbitrum.io` (443 HTTPS + WSS), `snapshot.arbitrum.foundation` (443, init only), and your own L1 RPC and beacon hosts. For other chains, allow that chain's sequencer, feed, and snapshot hosts, plus your parent-chain endpoints. **More outbound paths exist only if you enable them:** the version alerter (off by default), the classic redirect, or DA/REST endpoints on AnyTrust chains such as Nova.

</VanillaAdmonition>
