This page describes the recommended architecture for consuming the sequencer feed at scale.

**Audience:** infrastructure teams running fleets of Arbitrum (or Arbitrum chain) nodes on behalf of customers, such as RPC providers, explorers, and indexers.

**Not the audience:** operators running a single node for their own use. A single node pointed at the public feed is a fine setup. It will see periodic reconnects (see below), briefly trail the chain head during them, and always converge via parent chain batches. None of the machinery on this page is required for that case. See [How to run a feed relay](/run-arbitrum-node/run-feed-relay.mdx) for the basics.

## Summary

1. **Run your own feed relays.** At least two, in different geographic regions, with distinct egress IPs.
2. **Each relay maintains at least two primary upstream connections** to the upstream feed endpoint.
3. **Each node connects to at least two of your relays as primary feeds** (a list of primary URLs). Do not use the secondary/fallback mechanism for redundancy.
4. **Never point a node fleet directly at the public feed.** The relay layer exists to collapse your fleet's footprint to a handful of well-behaved upstream connections.
5. **Do not treat individual reconnects as incidents.** Alert on sustained absence of feed data and on sustained head lag, not on `readData returned EOF`.

If you follow 1-3, a disconnect on any single connection, relay, or region is invisible to your nodes.

## Feed reconnections are normal

The sequencer feed is a long-lived WebSocket. Long-lived connections get terminated in normal operation by every layer they cross:

- **Content delivery networks.** Public feed endpoints are fronted by Cloudflare. Cloudflare restarts edge servers whenever it rolls out code to its network, which drops the WebSocket connections those servers carry. This is documented, expected behavior: see the [Cloudflare WebSockets technical note](https://developers.cloudflare.com/network/websockets/#technical-note).
- **Load balancing and capacity changes.** When feed capacity scales up or down (for example, to absorb a traffic burst), connections are redistributed across instances. Every redistribution is a disconnect/reconnect for the affected clients.
- **Ordinary transit events.** Route changes, edge maintenance, and idle and lifetime limits along the path.

A healthy client sees this as:

```text
WARN readData returned EOF                        url=wss://... err="unexpected EOF"
INFO First reconnection attempt, skipping backoff url=wss://...
INFO Feed connected                               requestedSeqNum=...
```

with sub-second to few-second reconnection. Occurring a few times per day per connection, this is **normal operation, not degradation**. The architecture below exists so that these events never affect what your nodes see.

Two properties of the system bound the impact of any feed interruption:

- **The feed is a latency optimization, not the source of truth.** Every message is also posted to the parent chain in batches. A node that misses feed messages backfills them from the parent chain automatically. Feed loss can add seconds to minutes of head latency; it cannot cause data loss or an incorrect chain.
- **Messages carry monotonic sequence numbers**, so clients holding multiple simultaneous feed connections deduplicate perfectly.

## What happens on reconnect (and why gaps appear)

On reconnect, a client asks the server to resume from a requested sequence number. A feed instance can only replay what is in its own catchup buffer. After a capacity change, a reconnecting client may land on a fresh instance that does not hold the earlier history, and gets resumed at that instance's current position instead:

```text
WARN new message sequence number (34078876) is greater than the expected
     sequence number (34078551): remove previous segments from backlog
```

The node fills that gap from the parent chain. This is safe, but it is also exactly the event that multi-primary redundancy makes a non-event: with two or more simultaneous primaries, the other connection has been streaming the whole time and there is no gap to fill.

The corollary: **redundancy must live on the client side, as multiple simultaneous connections.** Server-side resume semantics cannot guarantee gapless delivery across a single connection's lifecycle.

## The reference architecture

```text
                 upstream feed endpoint (CDN-fronted)
                        wss://feed...
                     /   \                /   \
                    /     \              /     \
            +--------------+          +--------------+
            |   Relay A    |          |   Relay B    |     >= 2 relays,
            |  (region 1)  |          |  (region 2)  |     >= 2 primary upstream
            |  2 upstreams |          |  2 upstreams |     connections each,
            +--------------+          +--------------+     distinct egress IPs
                  |    \                  /    |
                  |     \                /     |
              [ node ]  [ node ]  [ node ]  [ node ]       every node: >= 2 relays
                                                           as PRIMARY feed inputs
```

### Layer 1: your relays

Run the [feed relay](/run-arbitrum-node/run-feed-relay.mdx) shipped with Nitro.

- **At least two relays, geographically distributed.** Edge and transit problems are usually regional (a single CDN point of presence, one provider's backbone). Two relays entering the network from different regions decorrelate those failures.
- **Distinct egress IPs, deliberately.** The feed load balancer routes connections to backends by client source IP (session affinity). All connections from one egress IP generally land on the same backend and stay there. Your effective upstream redundancy is therefore bounded by **how many distinct egress IPs you use**, not by how many relay pods or connections you run. Ten relays behind one NAT IP is one unit of redundancy.
- **At least two primary upstream connections per relay:**

```shell
relay \
  --chain.id=42161 \
  --node.feed.input.url=wss://arb1-feed.arbitrum.io/feed,wss://arb1-feed.arbitrum.io/feed \
  --node.feed.output.addr=0.0.0.0 \
  --node.feed.output.port=9642
```

The feed input accepts a comma-separated list of URLs. All of them are connected simultaneously and deduplicated by sequence number. Where a chain publishes only one public feed hostname, two connections to the same hostname from distinct egress IPs still provide meaningful redundancy (session affinity will generally pin them to different backends). Do not exceed two upstream connections per relay: each one doubles bandwidth, and excessive connections may be rate-limited at the edge.

### Layer 2: your nodes

Every node lists **at least two of your relays as primary feeds**:

```shell
nitro \
  --node.feed.input.url=ws://relay-a.internal:9642,ws://relay-b.internal:9642 \
  ...
```

Nitro connects to every URL in the primary list at the same time and dedupes by sequence number. A reconnect, restart, or regional problem on one relay is invisible: the other connection never stopped streaming.

### Why a primary list, not `secondary-url`

A common misconfiguration is `--node.feed.input.url=<own relay>` plus `--node.feed.input.secondary-url=<public feed>` as a "fallback." This does not do what operators expect:

- The secondary feed is **inactivity-triggered, not lag-triggered**. It activates only after roughly five seconds with _zero_ messages from the primary, and it deactivates again once the primary has been continuously healthy for a sustained period.
- It is **additive**: the secondary runs alongside the primary; it does not replace it. A relay that is behind but still streaming **never** triggers it, so it provides no protection against a lagging upstream.
- In practice, it silently multiplies your public feed footprint. A fleet where every node carries the public feed as secondary produces a large number of direct public feed connections that the operator did not intend to have, all subject to per-IP affinity and edge rate limiting.

Multiple primaries give you actual concurrent redundancy with none of these surprises. Reserve `secondary-url` for what it is: a last-resort input for total primary silence, if you use it at all.

### Never point the fleet directly at the public feed

Nitro's reconnect loop retries roughly every 15 seconds, per node, indefinitely. A fleet of direct clients aggregates into exactly the kind of per-IP connection pattern that edge protections rate limit, and a rate-limited client can stay banned precisely because it keeps retrying. Two relays collapse an arbitrarily large fleet into a handful of upstream connections. This is the single highest-leverage change a provider can make.

## Operational guidance for your fleet

- **Health checks:** do not mark a node unhealthy because it logged a feed reconnect. Gate on sustained head lag, with tolerance for brief catch-up bursts after a reconnect, where messages per second spike while the node drains the backlog.
- **Alert on state, not events:**
  - `arb_feed_sources_connected == 0` sustained for more than a minute (the node has no feed input at all)
  - head lag versus a reference RPC sustained beyond your latency SLO
  - relay upstream disconnect rate materially above its own baseline
- **Log lines:**

| Log line                                                            | Meaning                                                                                        |
| ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `readData returned EOF` followed by `Feed connected` within seconds | Normal reconnect. Not an incident.                                                             |
| `Compression was not negotiated ... non-critical`                   | Informational. Safe to ignore.                                                                 |
| `new message sequence number (...) is greater than the expected`    | Resume gap after reconnect; the node backfills from the parent chain. Rare with multi-primary. |
| `no connected feed` sustained, reconnects failing repeatedly        | Investigate: likely local egress, DNS, or an edge rate limit on your IP.                       |
| `BlockHash from feed doesn't match locally computed hash`           | Not a transport issue. Check the chain's status page and support channels before acting.       |

## Feed monitoring operated by Offchain Labs

Offchain Labs maintains continuous, alerting monitoring on the feed path end to end for the chains it operates infrastructure for. **If this reference architecture is followed and you still see sustained degradation, it is highly unlikely you are observing something that is not already known.** This monitoring includes:

- **Multi-region synthetic feed subscribers.** Always-on probe clients in multiple regions hold long-lived connections to the same public endpoints customers use, alerting on connection failures, message inactivity, and sequence number stalls.
- **Public feed canary nodes.** Full nodes deliberately consuming the public feed from outside Offchain Labs' own network, experiencing exactly what an external subscriber experiences.
- **Relay fleet metrics.** Every relay exports upstream connection state, connected client counts, and backlog depth, with alerting on upstream loss and backlog growth.
- **Transport-level monitoring.** Host network metrics (including TCP retransmit ratios) on feed infrastructure, which catch edge and transit degradation before most subscribers notice.
- **Sequencer-side publication alerting.** A stall in feed publication at the source pages the on-call rotation directly.
- **Edge analytics.** Per-location CDN error and connection-rate visibility for the public endpoints.

All of this pages a 24/7 on-call rotation, and incidents are published to the relevant chain's status page (for Arbitrum One and Nova: [status.arbitrum.io](https://status.arbitrum.io/)).

## Reporting an issue

Check the chain's status page first. If you still believe you are seeing a feed-side problem, include the following in your report; it turns a multi-day thread into a same-day answer:

1. Time window in **UTC**, as precise as possible.
2. The exact feed URL(s) affected.
3. Your topology: how many relays, where, upstream URL(s) per relay, and the exact `--node.feed.input.*` configuration on both relays and nodes.
4. Your egress IPs for the affected connections.
5. Sample logs around the event (the reconnect lines above, with timestamps).
6. Whether it self-recovered, and how long recovery took.
