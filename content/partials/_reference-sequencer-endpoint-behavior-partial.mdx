## Sequencer endpoint behavior

Arbitrum One has two public endpoints with different roles. The public RPC URL is for general use. The direct <Term id="sequencer">sequencer</Term> endpoint accepts only `eth_sendRawTransaction` and `eth_sendRawTransactionConditional`. The table compares their purpose and operational guarantees.

### The two endpoints at a glance

| Endpoint                                                          | Purpose                                                                                                                                           | Operational guarantees                                                                                                                                     |
| ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`https://arb1.arbitrum.io/rpc` (public RPC URL)**               | General-purpose read/write endpoint, useful for development and low-volume reads.                                                                 | **No uptime, latency, or rate-limit guarantees.** If your decentralized app depends on availability, use a third-party node provider or run your own node. |
| **`https://arb1-sequencer.arbitrum.io/rpc` (sequencer endpoint)** | Direct submission path to the chain's sequencer for write traffic. Accepts only `eth_sendRawTransaction` and `eth_sendRawTransactionConditional`. | Has the queueing and timeout behavior described below. It is still a best-effort public endpoint with no formal service-level agreement (SLA).             |

### Latency and timeout behavior

Under nominal load, the sequencer endpoint accepts a submission in well under a second. The sequencer places each submission in a bounded in-memory queue, with a default capacity of 1024. The queue timeout, 12 seconds by default, limits how long a transaction can wait in that queue. It isn't a guarantee of end-to-end inclusion time.

When a submission hits a queue limit, `eth_sendRawTransaction` behaves as follows:

- **Queue full:** it returns an error right away.
- **Queue timeout:** the sequencer drops the transaction. `eth_sendRawTransaction` has already returned the transaction hash, so you get no error and no receipt. The transaction is **not** included. Resubmit the same signed transaction, or re-sign it with the same nonce.

### Recommended fallback patterns

- Use a third-party node provider as your primary endpoint, or as a fallback when a direct sequencer submission fails.
- Retry on transient errors only. You can retry network and connection errors with backoff. Don't retry terminal errors such as `nonce too low`.
- If a transaction has no receipt by your deadline, check the sender's nonce before you resubmit. See [Handle transactions with no receipt](/arbitrum-essentials/arbitrum-vs-ethereum/migrate-transaction-submission#handle-transactions-with-no-receipt).

### Monitoring and alerting

A successful `eth_sendRawTransaction` response means the sequencer admitted your transaction into its queue. It does **not** mean the transaction is in a block. To confirm inclusion, poll `eth_getTransactionReceipt`. You can also send the transaction to an RPC node with `eth_sendRawTransactionSync`, which returns the receipt once the sequencer executes the transaction. For details, see [Transaction submission behavior](/arbitrum-essentials/arbitrum-vs-ethereum/transaction-submission).

Neither response means the transaction is posted to the parent chain in a batch or finalized there. If your application needs parent-chain finality guarantees, track that separately. For monitoring, alert on these cases:

- Submission calls that return errors or exceed your expected latency ceiling.
- Transaction hashes that never get a receipt.
