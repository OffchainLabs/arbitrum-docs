## Sequencer endpoint behavior

Arbitrum One has two public endpoints with different roles. The public RPC URL is for general use. The direct <Term id="sequencer">sequencer</Term> endpoint accepts only `eth_sendRawTransaction` and `eth_sendRawTransactionConditional`. The table compares their purpose and operational guarantees.

### The two endpoints at a glance

| Endpoint                                                      | Purpose                                                                                                                                           | Operational guarantees                                                                                                                                     |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `https://arb1.arbitrum.io/rpc` (public RPC URL)               | General-purpose read/write endpoint, useful for development and low-volume reads.                                                                 | **No uptime, latency, or rate-limit guarantees.** If your decentralized app depends on availability, use a third-party node provider or run your own node. |
| `https://arb1-sequencer.arbitrum.io/rpc` (sequencer endpoint) | Direct submission path to the chain's sequencer for write traffic. Accepts only `eth_sendRawTransaction` and `eth_sendRawTransactionConditional`. | Has the queueing and timeout behavior described below. It is still a best-effort public endpoint with no formal service-level agreement (SLA).             |

### Latency and timeout behavior

Under normal load, the sequencer endpoint accepts a transaction in less than a second. The sequencer puts each submission in a bounded in-memory queue. By default, the queue holds 1,024 transactions.

The queue timeout is 12 seconds by default. It limits how long a transaction can wait in the queue before the sequencer picks it up or rejects it. The timeout is **not** an end-to-end inclusion latency guarantee. If the sequencer does not pick up the transaction before the timeout, `eth_sendRawTransaction` returns `context deadline exceeded`. In that case, the sequencer did **not** accept the transaction, and you can safely retry it.

### Recommended fallback patterns

- Use a third-party node provider as your primary endpoint, or as a fallback when a direct sequencer submission fails.
- Retry only on transient errors. You can safely retry `context deadline exceeded` and network or connection errors with backoff. Do not retry terminal errors, such as `nonce too low` or contract reverts.

### Monitoring and alerting

A successful `eth_sendRawTransaction` response means that the sequencer has already put your transaction in an L2 block. The call returns only after the sequencer creates the block, not when it adds the transaction to the queue. Treat this response as the sequencer's <Term id="soft-confirmation">soft confirmation</Term>: the sequencer has ordered and executed your transaction.

The response does **not** mean that the transaction is posted in a batch to the <Term id="parent-chain">parent chain</Term>, or final there. If your app needs parent-chain finality, track it separately. For monitoring, alert on submission calls that return errors or take longer than your latency limit. Do not assume a pending-but-unconfirmed state.
