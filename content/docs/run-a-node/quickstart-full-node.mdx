This quickstart starts an <Term id="arbitrum-one">Arbitrum One</Term> full node with Docker, using the settings we recommend for a node that serves RPC requests. It takes four steps: prepare a data directory, start the node, confirm it syncs, and shut it down cleanly.

Every choice here is a default you can change later. To run a different chain, tune performance, or pick a different state scheme, read [how to run a full node for an Arbitrum chain](/run-a-node/run-full-node).

<Callout type="info">

If you want to access an Arbitrum chain without running your own node, see [RPC endpoints and providers](/arbitrum-essentials/reference/node-providers) for fully managed nodes hosted by a third party.

</Callout>

## What you need

- **A parent chain RPC endpoint.** Your node reads Ethereum through it. Self-host a client or use a provider.
- **An Ethereum beacon chain RPC endpoint.** See the [list of beacon chain RPC providers](/run-a-node/reference/l1-ethereum-beacon-chain-rpc-providers).
- **Docker**, and a user account that can run it.
- **About 5 TB of free disk space** for Arbitrum One. Read [plan your disk space](#plan-your-disk-space) before you provision the volume.

## The defaults this quickstart uses

| Setting            | This quickstart                              | Why                                                                                                                                     |
| :----------------- | :------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------- |
| Chain              | Arbitrum One (`arb1`)                        | The most common choice. To [run a different chain](#run-a-different-chain), change `--chain.name` and the parent chain endpoints.       |
| State scheme       | <Term id="hashdb">HashDB</Term>, the default | Simplest to initialize, and it supports block validation. [Compare it with PathDB](/run-a-node/run-full-node#choose-a-state-scheme).    |
| Initialization     | `--init.latest=pruned`                       | Downloads, verifies, and extracts the latest full node snapshot for you.                                                                |
| Validator strategy | Watchtower, the default                      | Your node checks onchain assertions and logs any disagreement. [Read about watchtower mode](/run-a-node/run-full-node#watchtower-mode). |
| Exposed ports      | `8547` (HTTP), `8548` (WebSocket)            | The standard RPC ports.                                                                                                                 |

<Callout type="warn" title="Keep RPC endpoints off untrusted networks">

The command below binds RPC to `0.0.0.0` so you can reach the node from your own machine. Public exposure raises the risk of out-of-memory crashes and of the node falling behind the chain. Keep the node behind a firewall.

</Callout>

## Plan your disk space

Arbitrum One requires a <Term id="database-snapshot">database snapshot</Term> on the first run, because the snapshot supplies state from the Classic era. The `pruned` snapshot is about 2.4 TB. Nitro needs room for the download and the extracted database at the same time, so plan for about 2x the snapshot size, then add headroom for chain growth.

Two problems account for most failed first runs, and you can avoid both:

- **`--init.download-path` defaults to `/tmp/`.** Inside a container, `/tmp/` sits on the image's writable layer, not on your mounted volume. The command below points this flag at the mounted volume, so the archive lands on your large disk.
- **The 2x requirement is temporary.** Nitro deletes the archive after it extracts, so the peak applies only during initialization.

<Callout type="idea" title="Running your first node? Start with Arbitrum Nova">

On Arbitrum One, the download and extraction take hours to days. Arbitrum Nova has the smallest snapshot of the DAO-governed chains, so it rehearses the whole flow fastest:

| Chain            | Pruned snapshot |
| :--------------- | :-------------- |
| Arbitrum One     | About 2.4 TB    |
| Arbitrum Sepolia | About 1.6 TB    |
| Arbitrum Nova    | About 580 GB    |

A testnet chain is not a small chain here. Arbitrum Sepolia still needs about 1.6 TB, so it saves you little over Arbitrum One. Run Nova first, then repeat on the chain you want. See [run a different chain](#run-a-different-chain).

Snapshots grow over time. Each one publishes a `metadata.json` that gives its current total size. Read it before you provision a disk. See [Nitro database snapshots](/run-a-node/reference/nitro-database-snapshots#downloading-the-snapshot-from-a-url).

</Callout>

## 1. Create the data directory

<Term id="arbitrum-nitro">Nitro</Term> stores its database at `/home/user/.arbitrum` inside the container. Mount a host directory there so the database survives restarts.

Create that directory **before** you start Docker. Otherwise Docker creates it as `root`, and the container, which runs as UID 1000, cannot write to it.

```shell
mkdir -p /some/local/dir/arbitrum/downloads
```

If you still get permission errors, see [note on permissions](/run-a-node/run-full-node#note-on-permissions).

## 2. Start the node

Replace the two endpoint placeholders with your own, then run:

```shell
docker run --rm -it \
  --name arbitrum-node \
  -v /some/local/dir/arbitrum:/home/user/.arbitrum \
  -p 0.0.0.0:8547:8547 \
  -p 0.0.0.0:8548:8548 \
  offchainlabs/nitro-node:v3.12.1-70fa99a \
  --parent-chain.connection.url=<Ethereum RPC URL> \
  --parent-chain.blob-client.beacon-url=<Ethereum beacon chain RPC URL> \
  --chain.name=arb1 \
  --init.latest=pruned \
  --init.download-path=/home/user/.arbitrum/downloads \
  --http.api=net,web3,eth \
  --http.addr=0.0.0.0 \
  --http.vhosts=* \
  --http.corsdomain=*
```

The node downloads the snapshot, verifies its checksum, extracts it, and then syncs to the head of the chain.

<Callout type="info">

If your parent chain client runs on `localhost`, add `--network host` immediately after `docker run` so the container can reach it.

</Callout>

## 3. Confirm the node is syncing

After initialization finishes, ask the node for its block number:

```shell
curl -X POST http://localhost:8547 \
  -H 'Content-Type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_blockNumber","params":[]}'
```

A result that climbs on repeated calls means the node follows the chain. Compare it against the [Arbitrum One block explorer](https://arbiscan.io/) to see how far behind you are.

To check whether the node still considers itself out of date, call `eth_syncing`:

```shell
curl -X POST http://localhost:8547 \
  -H 'Content-Type: application/json' \
  --data '{"jsonrpc":"2.0","id":1,"method":"eth_syncing","params":[]}'
```

A `false` result means the node has caught up.

## 4. Shut down cleanly

Give the node time to write its current state to disk. An abrupt stop can corrupt the database and force you to initialize from a snapshot again.

Stop the node by name, and give it up to 30 minutes to finish writing:

```shell
docker stop --timeout=1800 arbitrum-node
```

<Callout type="warn" title="Do not stop every container at once">

You may see `docker stop --time=1800 $(docker ps -aq)` in older instructions. Avoid it. `docker ps -aq` returns every container on the host, so the command stops your other workloads too. Docker also deprecated `--time` in favor of `--timeout`.

</Callout>

## Run a different chain

To run a different DAO-governed chain, change `--chain.name` and point the parent chain flags at that chain's parent:

| Chain            | Flag                          | Parent chain     |
| :--------------- | :---------------------------- | :--------------- |
| Arbitrum One     | `--chain.name=arb1`           | Ethereum mainnet |
| Arbitrum Nova    | `--chain.name=nova`           | Ethereum mainnet |
| Arbitrum Sepolia | `--chain.name=sepolia-rollup` | Ethereum Sepolia |

Arbitrum Sepolia settles to Ethereum Sepolia, so it needs Sepolia endpoints for both `--parent-chain.connection.url` and `--parent-chain.blob-client.beacon-url`. If you change only `--chain.name`, the node reads the wrong parent chain and exits at startup:

```text
CRIT [00-00|00:00:00.000] L1 chainID doesn't fit config    found=1 expected=11,155,111
```

To run a node for your own Arbitrum chain, the flags differ. You supply the chain's configuration, a <Term id="sequencer-feed">sequencer feed</Term> URL, and a forwarding target. See the [required parameters](/run-a-node/run-full-node#required-parameters) in the full how-to.
