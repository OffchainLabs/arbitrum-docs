This guide shows you how to connect to the <Term id="fast-feed">Fast Feed</Term> on <Term id="arbitrum-one">Arbitrum One</Term> and read the messages it publishes. To buy the ticket that admits your connection, follow [how to buy Fast Feed access](/how-arbitrum-works/priority-gas-auction/use-fast-feed) first.

## Prerequisites

- An API key bound to an active ticket. [How to buy Fast Feed access](/how-arbitrum-works/priority-gas-auction/use-fast-feed) shows how to generate the key and buy the ticket.
- The Fast Feed endpoint for your network, from [addresses and endpoints](/how-arbitrum-works/priority-gas-auction/use-fast-feed#addresses-and-endpoints). The examples read it from `$FEED_URL` and the raw key from `$API_KEY`.
- A WebSocket client. The examples use [wscat](https://github.com/websockets/wscat) or [websocat](https://github.com/vi/websocat) on the command line, the `ws` package for Node.js, and the `websockets` package for Python.

## Connect

Once the round in which you bought has ended, open a WebSocket to the Fast Feed endpoint and send your raw API key, not its hash, as a bearer token in the `Authorization` header of the upgrade request:

```text
Authorization: Bearer <your-api-key>
```

The endpoint hashes the key with Keccak-256, compares it against the active tickets, and only then completes the upgrade. Messages start flowing at once. You open one connection per ticket, and each connection receives the full feed. Three rules apply to every client:

- Complete the upgrade within 5 seconds, or the endpoint drops the socket.
- Send only ping and pong frames.
- Read as fast as the feed arrives. The endpoint drops a client that lags behind, so parse and process off the read loop.

Every frame is a binary WebSocket frame that carries one JSON object. The `kind` field of the object tells you what it holds: one transaction, or the end of a PGA round. Read `kind` first, then read the fields of that kind. The [what the Fast Feed publishes](#what-the-fast-feed-publishes) section lists every field.

<Tab value="Node.js">

```typescript
import WebSocket from 'ws';

const ws = new WebSocket(process.env.FEED_URL, {
  headers: { Authorization: `Bearer ${process.env.API_KEY}` },
});

ws.on('unexpected-response', (req, res) => {
  // 401: unknown key or no active ticket. 429: every ticket already has a connection.
  console.error(`Rejected: HTTP ${res.statusCode}`);
  req.destroy(); // with a listener attached, ws leaves the request open
});

ws.on('message', (data) => {
  const msg = JSON.parse(data.toString());
  const kind = msg.version === 1 ? 'Transaction' : msg.kind;
  switch (kind) {
    case 'Transaction':
      // msg.pga_round, msg.transaction.tx_hash, msg.transaction.receipt, ...
      break;
    case 'PGARoundEnd':
      // msg.pga_round, msg.block_number
      break;
    default:
      // Skip kinds that this client does not know.
      break;
  }
});

ws.on('close', (code, reason) => {
  console.log('closed', code, reason.toString());
});
```

```python
import asyncio
import json
import os

import websockets


async def main():
    headers = {"Authorization": f"Bearer {os.environ['API_KEY']}"}
    try:
        async with websockets.connect(os.environ["FEED_URL"], additional_headers=headers) as ws:
            async for frame in ws:
                msg = json.loads(frame)
                kind = "Transaction" if msg["version"] == 1 else msg.get("kind")
                if kind == "Transaction":
                    # msg["pga_round"], msg["transaction"]["tx_hash"], msg["transaction"]["receipt"], ...
                    pass
                elif kind == "PGARoundEnd":
                    # msg["pga_round"], msg["block_number"]
                    pass
                # Skip kinds that this client does not know.
    except websockets.InvalidStatus as e:
        # 401: unknown key or no active ticket. 429: every ticket already has a connection.
        print(f"Rejected: HTTP {e.response.status_code}")
    except websockets.ConnectionClosed as e:
        print(f"closed {e.rcvd.code} {e.rcvd.reason}")


asyncio.run(main())
```

This example needs `websockets` 14 or later. Older versions use `extra_headers=` instead of `additional_headers=`.

## What the Fast Feed publishes

The Sequencer sends each message as a JSON object inside a binary WebSocket frame, so byte fields arrive as hex-encoded strings. Every message starts with the same envelope fields. The `kind` field tells you which fields follow.

| Field          | Type             | Description                                                      |
| -------------- | ---------------- | ---------------------------------------------------------------- |
| `version`      | number           | Message format version: `1` or `2`                               |
| `kind`         | string           | The kind of message: `Transaction` or `PGARoundEnd`              |
| `timestamp_ms` | number           | Unix time in milliseconds when the Sequencer created the message |
| `pga_round`    | number, optional | The PGA round of the message, within the block, starting at 1    |

Skip every message whose `kind` your client does not know. The [reference client](https://github.com/OffchainLabs/nitro/tree/v3.12.4/cmd/transaction-feed-client) in the Nitro repository does the same.

<Callout type="info" title="A PGA round is not a ticket round">
  A PGA round is the 125ms ordering window inside a block. The `pga_round` field and the `PGARoundEnd` message refer to this round. A ticket round is the 24-hour period for which you buy Fast Feed tickets. Do not mix up the two.
</Callout>

### Transaction messages

A message with `kind` set to `Transaction` carries one transaction in a `transaction` object, plus the envelope fields. The `transaction` object carries the transaction itself:

| Field          | Type   | Description                                        |
| -------------- | ------ | -------------------------------------------------- |
| `block_number` | number | Tentative block number, not guaranteed to be final |
| `tx_index`     | number | Position within the block so far                   |
| `raw_tx`       | string | Hex-encoded, RLP-encoded signed transaction        |
| `tx_hash`      | string | Hex-encoded transaction hash                       |
| `receipt`      | object | Execution result                                   |

What the receipt reports:

- `status`
- `gas_used`
- `gas_used_for_l1`
- `cumulative_gas_used`
- `effective_gas_price`
- `base_fee`
- Any `contract_address` the transaction created
- The event `logs` emitted by the transaction

Each entry in `logs` carries three fields:

- `address`: the hex-encoded address of the contract that emitted the event
- `topics`: the hex-encoded topics of the event, in order
- `data`: the hex-encoded event data

### PGA round end messages

A message with `kind` set to `PGARoundEnd` tells you that the PGA round in its `pga_round` field has ended. No more transaction messages for this round will follow, so you do not have to wait for the first message of the next round to know that a round is complete. The Sequencer can drop messages under load, so a `PGARoundEnd` message does not prove that you received every transaction of the round.

The feed also sends this message for a round that has no transactions, and for a round that ends early because the block is full. FIFO ordering and delayed-message blocks send no `PGARoundEnd` message.

A `PGARoundEnd` message carries no `transaction` object. It adds one field to the envelope:

| Field          | Type   | Description  |
| -------------- | ------ | ------------ |
| `block_number` | number | Block number |

```json
{
  "version": 2,
  "kind": "PGARoundEnd",
  "timestamp_ms": 1759795200012,
  "pga_round": 3,
  "block_number": 1234
}
```

### Migrate from version 1

Version 1 messages have no `kind` field, and each one carries a transaction. Version 2 adds the `kind` field and the `PGARoundEnd` message, which has no `transaction` object. The fields of a transaction message are the same in both versions.

If your client reads every message as a transaction, update it as follows:

1. Read `kind` before you read `transaction`.
2. If `version` is `1`, treat the message as a `Transaction` message.
3. Skip every message whose `kind` your client does not know.

## Reconnect after a drop

If your connection closes, reconnect and continue from the current head. The Fast Feed keeps no history, so the messages sent while you were away are gone.

To keep a connection open from one round to the next, buy a ticket for every round, as described in [keep the connection across rounds](/how-arbitrum-works/priority-gas-auction/use-fast-feed#step-5-keep-the-connection-across-rounds).

## Troubleshoot

### Connection rejected or closed

| Response                                  | Cause                                                                          | Fix                                                                                     |
| ----------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `HTTP 401 Unauthorized`                   | The `Authorization` header is missing, or the key's hash has no active ticket. | Check the raw key and its hash. Tickets bought this round activate at `roundEnd`.       |
| `HTTP 429 Too Many Requests`              | The key already has as many open connections as it has active tickets.         | Close a connection, or buy more tickets for the next round.                             |
| `HTTP 426 Upgrade Required`               | The request was not a WebSocket upgrade, for example a plain HTTPS `GET`.      | Use a WebSocket client.                                                                 |
| Close `1008`, `authentication expired`    | The round ended and your key holds no ticket in the new round.                 | Buy before `roundEnd` each round, then reconnect.                                       |
| Close `1013`, `client lagged`             | Your client fell more than 2048 messages behind.                               | Drain the socket faster. Move parsing and processing off the read loop, then reconnect. |
| Close `1003`, `unexpected client message` | Your client sent a data frame.                                                 | Send only ping and pong frames.                                                         |
| Close `1011`, `server shutting down`      | The endpoint restarted.                                                        | Reconnect with a short backoff.                                                         |

## FAQ

**Do I need a Nitro node?**
No. The Fast Feed is a stream for your own client. To follow the chain, use the free [sequencer feed](/run-a-node/sequencer/read-sequencer-feed) instead.
