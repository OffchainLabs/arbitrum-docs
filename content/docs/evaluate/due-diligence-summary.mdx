This page is for risk, compliance and architecture reviewers at a financial institution. It answers the recurring due-diligence questions about Arbitrum One with a value, a source page in this documentation and the date that source states.

Last verified: 2026-10-15 against the linked pages.

The page covers Arbitrum One. Where a chain you launch yourself differs, the section [On your own Arbitrum chain](#on-your-own-arbitrum-chain) says how.

## What Arbitrum One is

Arbitrum One is a Rollup that executes transactions offchain and settles to Ethereum. The <Term id="arbitrum-rollup-protocol">Arbitrum Rollup protocol</Term> confirms its state on Ethereum.

| Claim               | Value                                                                                                                                                                             | Source                                                                            | Date stated by source |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- | --------------------- |
| Chain type          | The first permissionless Ethereum parent-chain Rollup with full Ethereum smart contract functionality, live on mainnet.                                                           | [Arbitrum: Understanding the risks](/arbitrum-essentials/reference/mainnet-risks) | none stated           |
| Data availability   | Rollup mode: all transaction data goes into the calldata or blobs of transactions submitted to the parent chain, so anyone can download and verify it.                            | [Data Availability](/run-a-node/data-availability)                                | none stated           |
| Data availability   | In the default Rollup mode, all transaction data is recorded onchain through calldata or blobs.                                                                                   | [Finality](/how-arbitrum-works/deep-dives/finality)                               | none stated           |
| Settlement          | Arbitrum executes offchain and uses Ethereum for settlement and data availability. Ethereum nodes store the compressed data and accept the result unless someone proves it wrong. | [Arbitrum introduction](/get-started/arbitrum-introduction)                       | none stated           |
| Contract deployment | Arbitrum is permissionless. Anyone can deploy any smart contract code.                                                                                                            | [Arbitrum: Understanding the risks](/arbitrum-essentials/reference/mainnet-risks) | none stated           |

## Guarantees

The protocol gives you these guarantees without trusting the operator. One honest <Term id="validator">validator</Term> is enough to keep the chain correct, and the <Term id="fraud-proof">fraud proof</Term> system makes that property <Term id="trustless">trustless</Term>.

Under <Term id="bold">BoLD</Term> this holds within a known, fixed time, regardless of how many adversaries take part.                                                       | [Inside Arbitrum Nitro](/how-arbitrum-works/inside-arbitrum-nitro)                      | none stated           |
| Correct execution         | The fraud proof system needs only one honest validator, and that validator can catch several malicious actors.                                                                                                                                                      | [Arbitrum introduction](/get-started/arbitrum-introduction)                             | none stated           |

## Trust assumptions

You trust one operator for speed and the parent chain for settlement. [Threat model and trust boundaries](/evaluate/threat-model) covers each assumption and its failure modes.

| Claim                 | Value                                                                                                                                                       | Source                                                                              | Date stated by source |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- | --------------------- |
| Sequencer operator    | On Arbitrum One, Offchain Labs currently runs the sequencer. There is no built-in mechanism to punish a misbehaving sequencer.                              | [Inside Arbitrum Nitro](/how-arbitrum-works/inside-arbitrum-nitro)                  | none stated           |
| Sequencer operator    | The sequencer is currently a single party on Arbitrum One.                                                                                                  | [Arbitrum glossary](/glossary#sequencer)                                            | none stated           |
| Soft finality         | A <Term id="soft-confirmation">soft confirmation</Term> is a sub-second provisional confirmation that depends on the sequencer behaving honestly.           | [The Sequencer and censorship resistance](/how-arbitrum-works/deep-dives/sequencer) | none stated           |
| Soft finality         | A malicious sequencer could reorder or censor transactions before they reach hard finality.                                                                 | [Finality](/how-arbitrum-works/deep-dives/finality)                                 | none stated           |
| Hard finality         | Security rests on the parent chain. Even if the sequencer misbehaves, transactions in posted batches are secured once finalized on the parent chain.        | [Finality](/how-arbitrum-works/deep-dives/finality)                                 | none stated           |
| Execution environment | <Term id="arbos">ArbOS</Term> is a trusted system component inside the State Transition Function. Every node and fraud prover replays it deterministically. | [ArbOS](/how-arbitrum-works/deep-dives/arbos)                                       | none stated           |

## Dispute economics

An attacker must bond ETH to post a claim and loses all of it when the claim is wrong.

| Claim                    | Value                                                                                                                                                                                              | Source                                                                           | Date stated by source |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- | --------------------- |
| Assertion bond           | <Var name="arbOneBaesStakeEth" /> ETH to post an assertion on Arbitrum One. Sub-challenge assertions require 555 ETH and 79 ETH per level. The cost applies to honest and malicious parties alike. | [BoLD FAQ](/how-arbitrum-works/bold/bold-faq)                                    | none stated           |
| Attacker outcome         | Honest parties are always refunded. Malicious actors always lose 100% of their bond, at each challenge.                                                                                            | [BoLD FAQ](/how-arbitrum-works/bold/bold-faq)                                    | none stated           |
| Above-budget attack      | An attacker can post several invalid assertions and open several challenges. One honest party can defend all of them in parallel, and extra challenges do not extend the delay.                    | [BoLD FAQ](/how-arbitrum-works/bold/bold-faq)                                    | none stated           |
| Honest party always wins | Arbitrum chains are deterministic, so only one history is correct. Anyone who knows the correct state can challenge a malicious claim and always win within a challenge period plus a small delta. | [BoLD: a technical deep dive](/how-arbitrum-works/bold/bold-technical-deep-dive) | none stated           |
| Bond pooling             | A bonding pool contract lets anyone crowdsource the bond from parties who want to help defend the chain.                                                                                           | [BoLD: a technical deep dive](/how-arbitrum-works/bold/bold-technical-deep-dive) | none stated           |

## Known risks

[Arbitrum: Understanding the risks](/arbitrum-essentials/reference/mainnet-risks) names three risks. Progressive decentralization: the Arbitrum DAO system owns Arbitrum One, and the Foundation's "State of Progressive Decentralization" page tracks what remains centralized. Software bugs: the codebase is audited and reviewed continuously, yet a non-zero chance of undiscovered vulnerabilities remains, so you decide how much value to entrust to the system. Scams: anyone can deploy any contract, so you interact with a contract on Arbitrum only when you have good reason to trust it, as on Ethereum.
