This page is for risk, security, and architecture reviewers. It answers four questions: who you trust, for what, what bounds each party, and what risk remains. It covers Arbitrum One first, then what changes on a chain you launch yourself. For the dated numbers, read the [Due-diligence summary](/evaluate/due-diligence-summary).

## The five trust boundaries

### Ethereum: settlement and data availability

You trust Ethereum for settlement, data availability, and hard finality. In Rollup mode, all transaction data goes into the calldata or blobs of transactions on the parent chain, so anyone can download and verify it ([Data Availability](/run-a-node/data-availability)). Hard finality rests on the consensus and integrity of the parent chain ([Finality](/how-arbitrum-works/deep-dives/finality#trust-considerations)).

Once a batch is posted to the Sequencer Inbox, only a <Term id="reorg">reorg</Term> of the parent chain can reorganize an Arbitrum chain. Fraud proofs and dispute resolution never cause a reorg ([Finality and chain reorganizations](/how-arbitrum-works/reference/finality-and-reorgs#the-reorg-model)). The <Term id="challenge-period">challenge period</Term> delays withdrawals back to Ethereum because that is where you cross a trust boundary; it does not affect transactions inside Arbitrum ([Arbitrum introduction](/get-started/arbitrum-introduction)).

### The sequencer: ordering and soft confirmation

You trust the <Term id="sequencer">sequencer</Term> for transaction ordering and for <Term id="soft-confirmation">soft confirmation</Term>: a sub-second provisional confirmation on the <Term id="sequencer-feed">sequencer feed</Term> that depends on the sequencer behaving honestly ([The Sequencer and censorship resistance](/how-arbitrum-works/deep-dives/sequencer)). On Arbitrum One, Offchain Labs runs the sequencer ([Inside Arbitrum Nitro](/how-arbitrum-works/inside-arbitrum-nitro)).

The sequencer cannot change execution. Once it commits to an ordering by posting a batch, it has no say over what happens next, and it can do nothing to compromise the chain's safety ([Arbitrum FAQ](/get-started/faq)). Execution belongs to the State Transition Function and ArbOS, which take the ordered input and return a block ([The Sequencer and censorship resistance](/how-arbitrum-works/deep-dives/sequencer)). The sequencer cannot skip or reorder <Term id="delayed-inbox">Delayed Inbox</Term> messages, and it cannot censor a transaction for good, because anyone can <Term id="forceinclusion">force inclusion</Term> after the delay window ([Forced transactions](/how-arbitrum-works/deep-dives/forced-transactions)).

What remains: a malicious sequencer can delay your transactions and has great power to front-run them, and there is no mechanism to punish a misbehaving sequencer ([Inside Arbitrum Nitro](/how-arbitrum-works/inside-arbitrum-nitro)).

### Validators: state assertions and disputes

You trust <Term id="validator">validators</Term> for the safety of the chain: they post bonded claims about the chain state and dispute each other ([Arbitrum FAQ](/get-started/faq)). Under <Term id="bold">BoLD</Term>, validation is permissionless: anyone can post an <Term id="assertion">assertion</Term>, bond, and defend the chain ([Inside Arbitrum Nitro](/how-arbitrum-works/inside-arbitrum-nitro#arbitrum-rollup-protocol)).

You do not have to trust any specific validator. Any one <Term id="honest-validator">honest validator</Term> can force the correct execution of the chain to be confirmed, with a bounded delay, no matter how many adversaries participate or how much they bond ([Inside Arbitrum Nitro](/how-arbitrum-works/inside-arbitrum-nitro#arbitrum-rollup-protocol)). This is what the docs call <Term id="trustless">trustless</Term> security. A validator that posts an invalid assertion cannot rewrite sequenced blocks; a rejected assertion only stops an invalid state from being confirmed ([Finality and chain reorganizations](/how-arbitrum-works/reference/finality-and-reorgs#the-reorg-model)).

### The chain owner and governance: upgrades

You trust the <Term id="chain-owner">chain owner</Term> for upgrades. Each chain has two <Term id="upgrade-executor">Upgrade Executor</Term> contracts that hold the critical affordances: the proxy admin of the parent-chain core contracts, the admin role of the core <Term id="rollup-contract">Rollup contract</Term>, and the `ArbOwner` precompile setters that set gas parameters and schedule ArbOS upgrades ([Ownership structure and access control](/launch-arbitrum-chain/operate/ownership-and-access#architecture)). On Arbitrum One, the chain owners are the <Term id="arbitrum-dao">Arbitrum DAO</Term> governance token system and a Multisig, the Security Council ([Ownership structure and access control](/launch-arbitrum-chain/operate/ownership-and-access#ownership-flexibility)).

The DAO-elected Security Council can, at any time, perform Emergency Actions or Non-Emergency Actions in accordance with its existing powers ([Troubleshoot Timeboost](/how-arbitrum-works/timeboost/troubleshoot-timeboost)). BoLD limits the scope of Arbitrum One's reliance on the Security Council but does not remove it ([BoLD FAQ](/how-arbitrum-works/bold/bold-faq)). The chain owner can also allowlist or pause the Inbox, which is the one exception to the force-inclusion guarantee ([Forced transactions](/how-arbitrum-works/deep-dives/forced-transactions#things-to-consider)). This boundary is the largest residual trust on Arbitrum One.

### ArbOS inside the State Transition Function

You trust <Term id="arbos">ArbOS</Term> as a system component. It is ordinary Go code compiled into the <Term id="state-transition-function">State Transition Function</Term>, so every node and fraud prover replays it deterministically ([ArbOS](/how-arbitrum-works/deep-dives/arbos)). It provides cross-chain communication, resource accounting, fee economics, and chain management ([Inside Arbitrum Nitro](/how-arbitrum-works/inside-arbitrum-nitro#arbos)).

Because ArbOS is inside the State Transition Function, the fraud-proof guarantee covers it: executing an Arbitrum chain is as trustless as executing an Ethereum chain ([Inside Arbitrum Nitro](/how-arbitrum-works/inside-arbitrum-nitro#arbitrum-rollup-protocol)). ArbOS upgrades go through the `ArbOwner` precompile, which the Upgrade Executor controls ([Ownership structure and access control](/launch-arbitrum-chain/operate/ownership-and-access#architecture)). What remains is the software-bug risk described in the table below.

## What you can watch yourself

You can detect an invalid assertion without bonding. A <Term id="watchtower-validator">watchtower validator</Term> never bonds and never takes an onchain action; it raises the alarm by whatever offchain means it chooses when it sees an invalid assertion. By default, all Arbitrum One nodes are watchtower validators ([BoLD FAQ](/how-arbitrum-works/bold/bold-faq)).

You can also choose how much trust each read of the chain carries. An Arbitrum node exposes three confirmation levels as block tags: `latest` is a promise from the sequencer, `safe` reverts only on a deep parent-chain reorg, and `finalized` reverts only if Ethereum reverts a finalized block. For crediting deposits, releasing funds, or any irreversible action, wait for `finalized`. Wait on the block tag, not on a fixed block depth ([Finality and chain reorganizations](/how-arbitrum-works/reference/finality-and-reorgs#recommended-confirmation-levels-for-indexers)).

## On your own Arbitrum chain

The same five boundaries apply, but you hold the chain-owner boundary. The chain owner is an address set by the deployer, and it can be an EOA, a Multisig, or a governance token system ([Ownership structure and access control](/launch-arbitrum-chain/operate/ownership-and-access#ownership-flexibility)). The Upgrade Executors give that address the proxy admin, the Rollup admin role, and the `ArbOwner` setters ([Ownership structure and access control](/launch-arbitrum-chain/operate/ownership-and-access#architecture)). Your reviewers must therefore review your own key management as the top trust assumption.

The sequencer boundary is also yours to configure. Each chain sets its own force-inclusion window ([Forced transactions](/how-arbitrum-works/deep-dives/forced-transactions#things-to-consider)), and chain owners decide whether to use the Censorship Timeout and can change its parameters ([The Sequencer and censorship resistance](/how-arbitrum-works/deep-dives/sequencer#censorship-timeout)).

An AnyTrust chain adds a sixth boundary. The <Term id="arbitrum-anytrust-protocol">AnyTrust protocol</Term> lowers costs by accepting a mild trust assumption ([AnyTrust Protocol](/how-arbitrum-works/deep-dives/anytrust-protocol)). Under its `2-of-N` assumption, a DACert proves that the block data will be available from at least one honest <Term id="data-availability-committee-dac">Data Availability Committee</Term> member ([AnyTrust Protocol](/how-arbitrum-works/deep-dives/anytrust-protocol)). If the batch poster cannot collect enough signatures, it falls back to posting full data on the parent chain; if you disable that fallback, a DAC outage halts the chain ([DAC/DAS Operations Guide](/launch-arbitrum-chain/chain-config/data-availability/dac-das-operations)).

Validation on your chain is permissioned by default. The docs recommend that you upgrade to BoLD but keep validation permissioned, because permissionless validation carries resource-exhaustion, infrastructure-cost, and liveness risks that the Arbitrum One parameters were tuned for ([BoLD for Arbitrum chains](/launch-arbitrum-chain/chain-config/validation/bold)). When `disableValidatorWhitelist` is `false`, only addresses in `validators[]` can post assertions. If assertions stop being confirmed for `validatorAfkBlocks` parent-chain blocks, anyone can disable the allowlist; setting `validatorAfkBlocks` to `0` removes that recovery path ([BoLD upgrade playbook for multisig and security council chains](/launch-arbitrum-chain/operate/bold-upgrade-playbook)).

Two options trade security for speed. <Term id="fast-withdrawals">Fast withdrawals</Term> add a committee trust assumption, a unanimous validator committee, and the docs recommend them mainly for AnyTrust chains. A shorter challenge period shrinks the window in which fraud can be challenged and weakens the chain's security model ([Monitor withdrawals programmatically](/arbitrum-bridge/withdrawal-monitoring)).

For the controls you can apply at each boundary, read [Compliance controls](/evaluate/compliance-controls). For monitoring and incident response, read [Operational assurance](/evaluate/operational-assurance).
